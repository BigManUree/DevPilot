# DevPilot 全方位测试报告

- 测试对象：DevPilot（Electron + NestJS + SQLite 本地开发工作台）
- 测试日期：2026-11-15
- 被测版本：`apps/backend` 0.1.0，schema v19（37 表），前端 Vite 5.4.21 + React
- 测试类型：黑盒、白盒（静态审查）、灰盒（库表 + 运行态）
- 测试规模：**执行用例 189 个**（黑盒/接口 105、灰盒 36、兼容 16、性能 14 组、边界 18），另跑既有质量门（单元 162、验收 24、类型检查 5 包）
- 结论：**功能主链路可用、既有测试全绿，但存在 3 个 P0 级安全缺陷（可被任意网页触发的本机命令执行、终端劫持、误杀无关进程），以及 6 个 P1 级功能/语义缺陷。**

## 四、缺陷清单（按严重级别）

### P0 · 安全（建议立即修复）

#### S-01 跨站表单请求可触发本机任意命令执行（CSRF → RCE）
- **现象**：任意网页只需一个 `<form>` POST（`application/x-www-form-urlencoded`，浏览器不预检）即可在用户机器上执行任意命令，且不经任何审批。
- **证据**（隔离实例 37150 实测）：
  ```bash
  curl -X POST http://127.0.0.1:37150/api/v1/tools/call \
    -H 'content-type: application/x-www-form-urlencoded' \
    -H 'Origin: https://evil.example.com' \
    --data-urlencode 'subjectType=user' \
    --data-urlencode 'tool=command.exec' \
    --data-urlencode 'params[command]=echo CSRF_RCE_OK'
  # → {"toolCallId":"51fa35ca-…","ok":true,"permission":"allowed",
  #    "data":{"pid":6792,"exitCode":0,"stdout":"CSRF_RCE_OK\r\n"}}
  ```
- **根因**：
  1. `apps/backend/src/main.ts` 只监听 127.0.0.1，但**没有任何鉴权**；
  2. `main.ts` 启用 `urlencoded({ extended: true })`，`params[command]` 被解析成嵌套对象，表单即可构造完整工具调用；
  3. `apps/backend/src/permissions/permission.service.ts:72` 对 `subjectType === 'user'` 直接 `allowed: true`，L3 高危分级在 user 主体上被短路；
  4. `subjectType` 来自请求体，调用方可任意声明身份；
  5. CORS 只限制响应读取，不阻止简单请求发送。
- **影响**：用户仅仅浏览网页即可被静默执行命令（删盘、下载执行、外联）。
- **修复建议**（按顺序做，1+2 即可断链）：
  1. 后端启动时生成进程级随机 token（`crypto.randomUUID()`），Electron 主进程通过 preload 注入渲染层；所有 REST 请求校验 `X-DevPilot-Token`（自定义头 → 浏览器跨站无法携带，天然免疫 CSRF）；MCP/CLI 走本地文件 token（`dataDir/.token`，0600）。
  2. `main.ts` 只对带 `X-DevPilot-Token` 的请求解析 `urlencoded`；或直接关闭 `urlencoded`（前端全部用 JSON）。
  3. `permission.service.ts`：`subjectType` 不再信任请求体，改为从 token 反推身份；user 主体也走 L3 检查（或至少对 `command.exec` 强制当次确认）。

#### S-02 WebSocket `Origin: null` 绕过 → 终端注入 / 事件窃听
- **现象**：用 `Origin: null` 连接 `ws://127.0.0.1:37100/ws` 成功，注入 `terminal.input` 后终端真实执行，并收到 5 条事件。
- **证据**：
  ```
  WS open with Origin:null (sandboxed iframe 来源)
  终端缓冲区含注入标记= true
  缓冲区片段: PS C:\…> echo WS_INJECTED WS_INJECTED
  收到事件数=5
  ```
- **根因**：`apps/backend/src/events.gateway.ts:56`
  ```ts
  const ok = ALLOWED_ORIGINS.has(origin) || origin.startsWith('file://') || origin === 'null';
  ```
  任何页面用 `<iframe sandbox="allow-scripts">` 发起的 WS，Origin 就是字符串 `null`，直接命中白名单放开。
- **影响**：等同本机 RCE（接管已有终端会话）+ 项目路径/日志/状态泄露。
- **修复建议**：删除 `origin === 'null'` 放行；改为 token 校验（`ws://127.0.0.1:37100/ws?token=…`），并对 `terminal.input` 二次校验 sessionId 归属。

#### S-03 端口接管无归属校验，停止时误杀无关进程
- **现象 A（实测造成真实故障）**：验收脚本的临时项目声明端口 5173，DevPilot 直接「接管」了本项目正在运行的 Vite（PID 15948），随后停止该项目时把 Vite 杀掉，前端开发服务器当场退出（exit 1）。
  ```
  [08:39:58] [WARN] 端口 5173 已有实例在运行（PID 15948），已接管为外部实例，未重复启动。点「停止」会终止该 PID。
  [08:40:01] [INFO] 已终止外部实例 PID 15948（端口 5173）
  ```
- **现象 B**：另外起一个无关 HTTP 进程占住 4215，项目启动返回 `Success（接管已在运行的实例）`，`tracked` 里记为 `adopted:true`，停止项目时该无关进程被杀（pid 6252, exitCode=1）。
- **根因**：`apps/backend/src/runtime/runtime.service.ts:346-380` 仅凭「端口监听 + HTTP 探测通过」判定接管，未校验 PID 是否属于本项目（命令行/工作目录/PID 血缘）；`stopService` 对 `adopted` 直接 `killTreeWait`。
- **影响**：误判启动成功；停止项目时杀掉用户其它程序（数据库、独立服务、甚至自己前端），有数据丢失风险。
- **修复建议**：
  1. 接管前校验 PID 归属：读 `wmic process where processid=<pid> get commandline,executablepath`（或 `Get-CimInstance`），命令行或工作目录命中 `project.root_path` 才允许接管；
  2. 不满足则返回冲突错误（`端口 X 被外部进程占用，是否终止/换端口？`），由用户显式选择，不自动接管；
  3. `adopted` 的停止加二次确认（前端弹窗「该实例非 DevPilot 拉起，确认终止？」）。

#### S-04 高危端点无二次确认（附带）
- `DELETE /api/v1/projects/:id?deleteFiles=true` 直接递归删除项目目录（实测把 fixture 整个目录删除，返回 `deletedFiles:true`）。
- `POST /api/v1/local-services` + `/:id/start` 可托管任意 exe；`POST /api/v1/terminal/sessions` 接受任意 `cwd`（实测 `C:/Windows`）。
- **建议**：删除文件、终止外驻实例、启动本地服务三类操作要求 body 里带 `confirm: "<projectName>"` 之类的显式确认字段，并在审计里区分 `user-confirmed`。

### P1 · 功能与语义

#### F-01 工作区无法新建文件（只能覆盖已有文件）
- **现象**：`POST /api/v1/workspace/file` 写不存在的路径一律 400：
  ```
  {"message":"路径不存在或不可访问：…\\newfile.txt","error":"Bad Request","statusCode":400}
  ```
  新建子目录下的文件同样失败；写已存在文件正常（`{"ok":true}`）。
- **根因**：`apps/backend/src/workspace/workspace.controller.ts:33` 对目标无条件 `fs.realpathSync(abs)`，文件不存在即抛错。工具网关 `assertFsPath` 已有「不存在则校验父目录」的写法，控制器没用上。
- **修复**：try realpath → catch 时对 `path.dirname` 做 realpath 再拼接 basename（与 `tool-gateway.service.ts:assertFsPath` 保持一致）。

#### F-02 无 LLM Key 时，启动失败原因被 Agent 报错覆盖
- **现象**：故意把启动命令写成不存在的 `devpilot-no-such-command --version`，任务耗时 **13.6s** 后失败，报告是：
  ```
  Agent 判断该项目无法通过自动修复解决：修复 Agent 调用失败：Error: all providers failed
  （尝试链：deepseek:TypeError: fetch failed | openai:no-key | moonshot:no-key …）
  最近日志：（跳过全量探测）
  ```
  用户看不到「命令不存在」这一真实原因。
- **根因**：`autostart.service.ts` 修复闭环在诊断前先调 LLM；provider 全失败后把 LLM 错误当作结论；`verifyRunning` 的 light 分支写入的 `（跳过全量探测）` 混进了「最近日志」。
- **修复**：`runSingle/runMulti` 在进入修复前先做**确定性判别**（命令可解析？`where/which` 是否存在？exit code 是否 127/9009？），命中即直接给出可读结论并跳过 LLM；LLM 不可用时输出「本机未配置模型，已跳过 AI 诊断」而不是 `all providers failed`。

#### F-03 依赖预检每次启动都重跑，固定多花 2.2s 并污染仓库
- **现象**：同一项目连续三次启动分别 **3512 / 3462 / 3346ms**，步骤里每次都出现「检测到 node 项目的 node_modules 缺失，已自动安装依赖」；手动 `mkdir node_modules` 后再启动降到 **1203ms**。同时项目里被写入 `package-lock.json`（原仓库没有）。
- **根因**：`apps/backend/src/runtime/auto-fixer.service.ts:104` 仅以 `fs.existsSync(rootPath/node_modules)` 判定；无依赖项目 `npm install` 不会生成 `node_modules` 目录 → 每次启动都重新安装。
- **修复**：
  1. `package.json` 无 `dependencies/devDependencies`（或全空）时直接跳过；
  2. 安装成功后写 `.devpilot/deps.stamp`（记录 `package.json`/锁文件 hash + 时间），命中即跳过；
  3. 安装前记录锁文件是否存在，若原本没有且安装后新生成，提示「DevPilot 生成了 package-lock.json，是否保留」。

#### F-04 资源不存在/参数非法统一返回 500
- 15 个用例返回 `{"statusCode":500,"message":"Internal server error"}`，包括：不存在的 project/task/approval/service、`limit=abc`、`offset=99999999999999999999`、空对象创建服务、`memories` 的 `scope` 非法、空 `tools/call`、`Content-Type: text/plain` 的 POST。
- **根因**：service 层大量 `throw new Error(...)`（非 Nest 异常）；`Number(limit)` 未校验 → `NaN` 进 SQL；控制器无 DTO 校验；无全局异常过滤器。
- **修复**：加 `ValidationPipe` + DTO；把业务错误统一改 `NotFoundException/BadRequestException/ConflictException`；加全局 `ExceptionFilter` 把未知异常映射为 500 但保留 `code` 与 `traceId`；对 `limit/offset` 做 `Number.isInteger && 1..1000` 校验。

#### F-05 未知工具静默返回成功
- `POST /tools/call` 传 `tool: "no.such.tool"` → `{"ok":true,"permission":"allowed"}`（`dispatch` 的 switch 没有 default，返回 undefined）。
- **修复**：`dispatch` 增加 default 抛 `BadRequestException('unknown tool')`；controller 侧对 `tool` 做枚举校验。

#### F-06 空请求体创建垃圾任务
- `POST /tasks` 传 `{}` → 201 并落库一条 `project_scope=null, input_summary=null, status=Pending` 的任务（已手动删除 `9e207673-…`）。
- **修复**：DTO 必填校验（至少 `projectId` 或 `title` + 非空 `input`）。

#### F-07 失败写入残留临时文件
- 只读文件写入失败后，项目目录留下 `readonly.txt.90f321e7-….tmp`（`tool-gateway.service.ts:fsWrite` 的 catch 分支未清理）。
- **修复**：`try/finally` 里 `fs.rmSync(tmp, {force:true})`。

### P2 · 性能

#### P-01 `GET /system/update-check` 同步 `execSync` 阻塞整个事件循环
- **证据**：清单指向 4s 才响应的地址时，
  - 基线 `/health` 中位 **1.2ms**；
  - 触发 update-check 期间首个 `/health` **4036ms**（其余恢复正常）；
  - update-check 单次 **5825ms**；5 个并发 **20719ms**（完全串行）。
- **根因**：`apps/backend/src/system.controller.ts:67` 用 `execSync('node -e "fetch(...)"')` 取清单。
- **修复**：改 `await fetch(url, {signal: AbortSignal.timeout(5000)})`；结果缓存 10 分钟；失败返回 `error` 字段而不抛。

#### P-02 环境探针接口无缓存，单次 1.1s，10 并发 14s
- `GET /environments` 30 次：P50 **1161ms**、P95 **1232ms**（每次 15 个探针全跑）；
- `GET /environments/scan-versions` 10 并发：每请求 **13.7s**，总墙钟 **14.2s**（串行执行器）。
- **修复**：加 60s TTL 内存缓存 + 进行中请求合并（single-flight）；`scan-versions` 用并发池（限 4）替代串行。

#### P-03 无端口服务固定空等 ~3.4s
- 常驻不绑端口的服务启动 **4569ms**（同项目有端口的服务 1203ms）。
- **根因**：`runtime.service.ts` 无端口常驻判定窗口 3s + `verifyRunning` 无端口分支再等 1.5s。
- **修复**：无端口服务改为「子进程存活 + 输出静默 N 毫秒 + 无 ERROR 日志」即判成功（N=800ms 可配），把 3s 窗口降为兜底上限。

#### P-04 数据目录无清理策略
- 真实数据目录 26MB：`devpilot.backup.v*.db` **12 个共 15MB**（每次迁移一份，永不清理）；`logs/` 1.8MB 按天累积无保留上限。
- **修复**：迁移备份保留最近 3 份；日志按天保留 7 天（启动时清理），并给「数据清理」入口。

其他资源观测：后端 RSS ~110MB；Electron 4 进程合计 ~410MB（主进程 115MB，GPU/渲染/工具进程 137+103+57MB）。

## 六、优化建议（按投入产出排序）

### 第一优先：安全（1–2 天，阻断 P0）
1. **本机 token 鉴权**：后端启动生成 `crypto.randomUUID()`；Electron 主进程经 preload 注入渲染层；REST 校验 `X-DevPilot-Token`，MCP/CLI 读 `dataDir/.token`。一个中间件即可，一次性断掉 CSRF 与身份伪造（S-01、S-04）。
2. **删除 `origin === 'null'`**（`events.gateway.ts:56`），WS 改为 query token 校验（S-02）。
3. **端口接管加 PID 归属校验**（`runtime.service.ts:346`），不匹配则报冲突让用户选择（S-03）。
4. **危险操作确认字段**：`deleteFiles`、停止 adopted 实例、启动本地服务，要求显式 confirm（S-04）。

### 第二优先：正确性与语义（2–3 天）
5. 全局 `ValidationPipe` + DTO；`throw new Error` → `NotFoundException/BadRequestException`；`limit/offset` 类型化（F-04、F-06）。
6. `dispatch` 的 default 分支（F-05）；`fsWrite` 的 tmp 清理（F-07）。
7. 工作区新建文件走父目录 realpath（F-01，5 行改动）。
8. 依赖预检加 stamp/跳过逻辑（F-03，约 20 行）。
9. 启动失败先做确定性判别再调 LLM（F-02）。

### 第三优先：性能（2 天）
10. `update-check` 改异步 + 10 分钟缓存（P-01）。
11. 环境探针加 60s TTL 缓存 + single-flight；`scan-versions` 并发池（P-02）。
12. 无端口服务判定改「存活 + 静默 + 无 ERROR」（P-03），预计 4.6s → 1.2s。

### 第四优先：工程化（持续）
13. 数据目录清理：迁移备份保留 3 份、日志保留 7 天（P-04）。
14. 前端按域拆分 `App.tsx`（2250 行）+ 路由懒加载。
15. 把本报告的 `.audit-qa/*.mjs` 收编为 `tests/qa/*` 并在 CI 中以 `DEVIPILOT_BACKEND_PORT=37150` 跑（沿用现有隔离原则）。
16. 修正 README/`docs/testing.md` 的计数漂移（C-07）。
