# 启动性能优化报告（冷启动 ≤5s）

> 实测日期：2026-11-17 · 本机 Windows 11 / Node 22.22.2 / Electron 33.4.11 / better-sqlite3(WAL) / 库 2.9MB、9 个项目
> 复测命令：`pnpm bench:startup`（打包态）、`pnpm bench:startup:dev`（开发态）、`node scripts/startup-ui-bench.mjs --exe <exe>`

## 结论

**目标达成：打包态从「窗口 2.3s 才出现、期间纯白屏」变为「窗口 0.45s 出现并画出品牌启动骨架，1.78s 工作台真实数据可见」。** 全部路径均在 5s 预算内，含冷缓存（首次启动）场景。

| 指标（打包态，主进程创建为 0 点） | 优化前 | 优化后 | 提升 |
|---|---|---|---|
| 窗口出现（MainWindowHandle 非零） | 2299 ms | **446 ms** | −80% |
| 窗口出现前的用户可见画面 | 纯白（无任何内容） | 品牌骨架 + 进度条（约 0.65s 可见，受渲染进程启动限制） | — |
| 渲染层首帧 | 未度量（≈窗口出现 + 0.1~0.5s） | **847 ms** | — |
| 后端可服务（listen + 探测到） | ≈1926 ms（在窗口之前同步等待） | **1674 ms**（与窗口并行，不再阻塞） | −13%（且不再进关键路径） |
| 工作台真实数据可见（CDP 口径） | 2437 ms | **2187 ms** | −10% |
| 应用内口径 dashboardReady | — | **1782 ms** | — |
| 冷缓存首次启动（清空编译缓存后首跑） | 未单独度量（同上再加盘/AV 冷读） | 首帧 1.9~3.0s / 数据 3.4~4.0s | 仍在 5s 内 |
| 进程树内存 | 464 MB | 359 MB | −22% |

数据来源：`docs/perf/startup-bench-*.json`、`docs/perf/startup-ui-bench-*.json`、`docs/perf/startup-dashboard-after.png`。

## 改了什么

### 1. 启动顺序重构：窗口先行、后端并行（`apps/desktop/src/main.ts`）
- 旧：`await backend.ensure()` → 再 `createWindow()`。后端 1.9s 的启动时间直接变成用户的白屏时间，且 Electron 自身 0.9s 初始化完全串行浪费。
- 新：
  - 主进程模块加载即 `backend.ensure()`（`main.ts:27`），与 Chromium 初始化并行；
  - `app.whenReady` 里**先注册 IPC、立刻建窗**（`main.ts:159`、`main.ts:186`），后端就绪后再执行托盘、更新检查、审批轮询等旁路任务（`main.ts:189`）；
  - 后端失败不再是无窗挂死，窗口已在，直接弹可见错误（`main.ts:206`）；
  - 窗口 `backgroundColor` + `backgroundThrottling:false`，避免首帧白闪与被节流拖慢（`main.ts:91`）。

### 2. 渲染层就绪门：请求排队而不是失败（`apps/desktop/src/preload.ts`、`apps/renderer/src/api.ts`）
- preload 新增 `backendReady()` / `onBackendReady()` / `startupMark()`（`preload.ts:8-19`）。
- `api.ts` 中所有请求先 `await whenBackendReady()`（`api.ts:74`）：窗口早于后端打开时，请求排队等放行，不会出现「启动瞬间一串 ECONNREFUSED toast」，骨架屏能正常显示。
- `getAuthToken` 旧实现固定轮询 3s（20×150ms）；改为「等后端就绪 → 读 30×50ms」（`main.ts:139`），token 只会在后端写入后才读，避免读到上一轮的过期 token。

### 3. 首帧可见：内联启动骨架（`apps/renderer/index.html`）
- 内联 CSS/HTML 骨架，不依赖 1.27MB JS 解析：HTML 解析完（约 0.65s，瓶颈是渲染进程启动而非脚本）即有品牌与进度条，React `createRoot().render` 时自动替换；这之前窗口由 `backgroundColor` 兜底，不闪白。
- 主题跟随 `data-theme`，暗色下不闪白。

### 4. 后端启动削减（`apps/desktop/src/backend-manager.ts`、`apps/backend/src/agents/model.service.ts`）
- 就绪探测间隔 300ms → 50ms（`backend-manager.ts:105`）：旧实现后端已 listen 后最多白等 300ms，而这段时间正好卡在建窗之前。
- `NODE_COMPILE_CACHE`（`backend-manager.ts:84`）：Node 22 模块编译缓存，二次启动省 200~300ms（实测后端 spawn→health 1703ms → 1392~1503ms）。
- `undici` 改为懒加载（`model.service.ts:4-16,221,234`）：它只服务 LLM 出站请求，却在启动期被整条模块图 eager require（实测 103ms）。
- 后端自带启动埋点（`apps/backend/src/startup-trace.ts`）：与主进程共用 0 点（`DEVIPILOT_STARTUP_T0`），Nest 各阶段耗时可直接看。

### 5. 启动耗时变成可观测、可回归
- `apps/desktop/src/startup-trace.ts`：主进程 + 渲染层 + 后端统一写 `<APPDATA>/devpilot/startup-trace.jsonl`（自动滚动保留 400 行，`DEVIPILOT_STARTUP_TRACE=0` 可关）。
- `scripts/startup-bench.mjs`：打包/开发态冷启动实测，输出首帧、窗口出现、后端就绪、首数据、内存，多轮取中位数并落 JSON。
- `scripts/startup-ui-bench.mjs`：用 Electron 远程调试口（CDP）轮询 DOM，测「工作台真实数据可见」——旧构建没有埋点也能测，因此可用于跨版本对比。
- 入口：`pnpm bench:startup` / `pnpm bench:startup:dev`。

## 尚未做（backlog，按收益排序）

1. **路由级代码分割——实测后降级（不建议做）**：主包 1.27MB，但拆开量化后（一次 manualChunks + 首屏最小集构建实验）：
   - antd 家族 636KB（50%）、其它三方 331KB（26%）、react 142KB（11%）、业务代码 162KB（13%）；
   - 「Shell + Dashboard + antd 主题」的最小首屏构建仍有 **1060KB**，因此懒加载其余 18 页最多只能推迟 **约 210KB（16.5%）**，按当前解析速度约省 **80~150ms**（首帧 0.85s → ~0.75s），远达不到 0.5s；
   - 代价是 2250 行 `App.tsx` 拆分 + 18 个页面的回归面 + 每个 chunk 都要处理 Suspense/首帧闪烁。
   **收益 / 风险明显不划算，暂不做。** 若确实还要压首屏 JS，优先级应是「削减首屏 antd 组件面（Dashboard 的 Drawer/Select/Tabs）」或直接不动。
2. **后端常驻/热重启——需先补齐四条前提（不建议直接开）**：复用常驻后端时实测窗口 0.24s、首帧 0.82s、数据 0.95s（`backend.reused@139`），收益确定。但直接开会带来四个真实故障面：
   - **版本/构建错配**：`BackendManager.ensure()` 只做 TCP 探测（`backend-manager.ts:65`），复用时不校验版本；`/health` 里的 `version` 目前是硬编码 `0.1.0`（`health.controller.ts:7`）。应用更新后旧后端进程仍占 37100 → 新前端跑旧后端代码、schema 版本对不上。必须先把 `version` 换成构建期注入并做握手，不匹配就强制重启后端。
   - **语义变化**：`RuntimeService.onApplicationShutdown` 会在后端退出时杀掉它拉起的服务（`runtime.service.ts:46-52`）。后端常驻后，用户关掉 DevPilot 但 dev server 还在跑 —— 对一部分人是好事，对另一部分是「我关了它还在动」的事故，必须是显式开关 + UI 明示。
   - **文件锁与运维路径**：常驻后端持有 `devpilot.db`（WAL）与 0600 token；备份/恢复/迁移（`applyPendingRestore`）都假设启动期独占数据库。
   - **孤儿进程**：卸载/更新时不结束的后端进程会持续监听本机端口，需要空闲超时 + 单实例互斥 + 设置页「立即退出后端」。
   结论：属于产品决策 + 一条独立的小型工程（版本握手 + 空闲超时 + 单实例 + 开关），不是顺手能加的优化。
3. **后端单文件打包**：`require` 图（Nest 2000+ 文件）占后端启动 ~1.2s，用 esbuild 打成单文件可减模块解析开销；但 Nest 装饰器 + better-sqlite3 原生模块需仔细处理，改动面较大。
4. 数据量增长后的复测：当前 2.9MB / 9 项目，库到 100MB 量级需重跑 `/projects`、`/environments` 与迁移检查。

## 复现命令

```bash
# 打包态冷启动（默认取 apps/desktop/release/win-unpacked/DevPilot.exe；旧基线 pack-out 已于 2026-11-17 清理）
pnpm bench:startup --runs 3

# 开发态（electron + apps/desktop）
pnpm bench:startup:dev

# 界面数据可见时间（可跨版本对比，走 CDP）
node scripts/startup-ui-bench.mjs --runs 3

# 原始时间轴
node -e "const l=require('fs').readFileSync(process.env.APPDATA+'/devpilot/startup-trace.jsonl','utf8').trim().split('\n').map(JSON.parse);console.table(l.slice(l.map(m=>m.mark).lastIndexOf('process.start')).map(m=>({mark:m.mark,ms:m.sinceProcessStartMs})))"
```

> 注：在宿主 CLI 的 shell 里跑 Electron 时必须清掉 `ELECTRON_RUN_AS_NODE` / `NODE_OPTIONS`，否则主进程会以纯 node 模式启动并瞬间退出（两个 bench 脚本已内置处理）。
