# DevPilot 产品需求整理文档

> 文档版本：V1.0（需求确认阶段整理稿）\
> 整理日期：2026-11-09\
> 产品名称：DevPilot\
> 产品定位：面向本地开发环境的跨平台桌面项目管理器与 AI Agent
> 自动化运行平台。

------------------------------------------------------------------------

## 1. 产品背景与目标

### 1.1 用户痛点

用户在本地开发了多个不同技术栈的项目，但没有可供 24
小时运行的服务器，因此需要在本机按需启动项目。当前操作流程繁琐：

-   每次都要查找项目根目录。
-   需要手动点击不同项目的启动脚本。
-   有些项目需要先打开 PyCharm、IntelliJ IDEA、Android
    Studio、微信开发者工具等 IDE 或官方工具。
-   有些项目需要进入项目目录，再手动执行
    `npm run dev`、`mvn spring-boot:run` 等命令。
-   前后端分离项目通常需要分别启动多个服务，并处理启动顺序和依赖关系。
-   启动脚本可能不完善，出错后还要手动查看日志、修改脚本或配置。
-   项目被删除后，还需要手动清理启动器中对应的项目记录。
-   不同语言、框架、IDE、模拟器和运行环境的启动方式不统一。

### 1.2 产品目标

DevPilot 希望提供一个统一的本地桌面入口，使用户能够：

1.  将本地项目或已有启动脚本导入软件。
2.  自动识别项目技术栈、目录结构、服务组成和启动方式。
3.  由 AI 生成可审阅的项目启动配置。
4.  在界面中一键启动、停止、重启单个服务或整个项目。
5.  管理前端、后端、数据库、缓存及其他关联服务。
6.  联动浏览器、IDE、微信开发者工具、Android 模拟器等外部工具。
7.  在界面中查看实时日志、运行状态和错误信息。
8.  由 AI 在授权范围内诊断错误、修复配置或代码并重试。
9.  支持项目、启动配置和外部工具的添加、修改、删除及维护。

## 2. 第一轮：产品形态

**状态：已确认**

-   DevPilot 采用跨平台桌面软件形态。
-   产品不是单纯的脚本收藏夹，而是集项目管理、服务编排、外部工具联动和
    AI Agent 于一体的本地开发管理器。

## 3. 第二轮：操作系统支持范围

**状态：已确认**

### 3.1 目标操作系统

-   Windows
-   macOS
-   Linux

### 3.2 开发与发布策略

-   第一版优先完成 Windows。
-   后续适配 macOS 和 Linux。
-   从第一版开始采用跨平台架构，避免后续重写核心业务。

### 3.3 架构要求

操作系统差异应通过适配层隔离，至少覆盖：

-   命令行与 Shell 差异。
-   文件路径与权限差异。
-   进程创建、进程树和终止方式差异。
-   外部工具发现与启动方式差异。
-   安装包和自动更新方式差异。

## 4. 第三轮：项目导入方式

**状态：已确认**

DevPilot 支持以下六种项目导入方式：

  标识      导入方式           说明
--------- ------------------ ------------------------------------
  folder    选择项目文件夹     使用系统文件选择器选择项目根目录
  drag      拖拽导入           将项目文件夹拖入软件窗口
  script    导入已有启动脚本   导入 BAT、PowerShell、Shell 等脚本
  git       Git 仓库导入       输入仓库地址，克隆到本地并识别
  archive   压缩包导入         导入 ZIP 等压缩包，解压后识别
  scan      自动扫描指定目录   扫描用户配置的常用项目目录

### 4.1 统一导入流程

六种导入方式最终汇总到统一的项目识别流程，不应分别维护六套项目管理逻辑。

### 4.2 项目删除与清理

产品总体需求包括：本地项目删除后，用户可以在 DevPilot
中删除对应项目及其启动配置。删除项目记录、删除启动配置和删除磁盘上的项目文件应区分处理，并在涉及磁盘文件删除时提供明确确认，避免误删。

## 5. 第四轮：项目自动识别与 AI 启动配置生成

**状态：已确认**

### 5.1 智能识别程度

选择：**完全智能化**。

AI 应尽可能分析：

-   项目类型、语言和框架。
-   项目目录结构。
-   前端、后端及其他服务组成。
-   依赖管理工具和依赖文件。
-   所需运行环境及版本线索。
-   数据库、缓存等外部依赖。
-   各服务启动命令和工作目录。
-   服务之间的依赖关系及启动顺序。
-   项目可能需要联动的 IDE、浏览器或模拟器。

### 5.2 无法识别时的处理

选择：**向用户追问**。

当 AI
无法确定项目类型、启动命令、工作目录、服务依赖或外部工具时，应向用户提出明确问题，收集必要信息后继续分析，而不是猜测并直接执行。

### 5.3 启动配置生成后的处理

选择：**预览确认后保存和执行**。

AI 生成的配置必须先展示给用户检查，用户确认后才能保存并执行。

### 5.4 结构化配置原则

启动配置不应仅仅是一个 BAT 或 Shell
文件。应采用结构化配置描述项目、服务、命令、工作目录、环境变量、依赖关系、健康检查和外部工具动作，以便跨平台执行和后续扩展。

## 6. 第五轮：多服务项目启动与管理

**状态：已确认**

### 6.1 启动方式

选择：**单服务独立启动 + 整个项目一键启动**。

-   用户可以单独启动、停止或重启某个服务。
-   用户也可以一键启动整个项目。
-   项目可以由多个服务组成。

### 6.2 服务依赖关系

选择：**AI 自动分析并允许用户调整**。

AI 分析服务之间的依赖和启动顺序，用户可以在界面中检查、调整和保存。

例如：

``` text
校园管理系统
├── MySQL
├── Redis
├── Spring Boot 后端
└── Vue 前端
```

启动时应尽可能先启动依赖服务，并在满足条件后启动依赖它们的服务。

### 6.3 单个服务启动失败时

选择：**仅标记失败服务，其他服务继续运行**。

-   失败服务显示错误状态。
-   其他无依赖关系的服务继续运行。
-   依赖失败服务的后续服务应根据依赖策略决定是否等待、跳过或标记为受阻。
-   日志和错误信息应关联到具体服务。

### 6.4 停止整个项目

选择：**停止全部服务及关联子进程**。

技术要求：

-   记录每次启动会话及其创建的进程。
-   追踪进程树或使用平台支持的进程组机制。
-   停止时只处理 DevPilot 创建或明确纳入该启动会话的进程。
-   不得仅凭进程名称误杀其他项目或用户进程。
-   需要考虑优雅停止、超时后强制终止及停止结果记录。

### 6.5 项目与服务的关系

建议采用两层模型：

-   项目：承载完整开发项目及其配置。
-   服务：项目中的独立运行单元。

同一个公共服务（例如本地 MySQL 或
Redis）未来可能被多个项目共享，因此应考虑服务复用及引用关系。

## 7. 第六轮：外部开发工具联动

**状态：已确认**

### 7.1 已确认的工具范围

  工具类别       具体工具或范围
-------------- -------------------------------------------------
  浏览器         Chrome、Edge、Firefox 等
  小程序工具     微信开发者工具
  Android 开发   Android Studio
  Android 运行   Android 模拟器
  Java IDE       IntelliJ IDEA
  Python IDE     PyCharm
  通用编辑器     Visual Studio Code
  数据库管理     Navicat、DBeaver、DataGrip 等
  容器工具       Docker Desktop
  终端工具       Windows Terminal、PowerShell、macOS Terminal 等
  其他 IDE       HBuilderX、Visual Studio
  自定义工具     用户自定义的其他外部程序

### 7.2 联动深度

选择：**打开工具并尽可能获取状态和执行结果**。

建议分级实现：

1.  **基础联动**：检测安装位置、打开外部工具、打开指定项目或目录。
2.  **命令联动**：调用 CLI 或官方命令接口，获取构建和运行结果。
3.  **深度联动**：在工具提供 API、CLI
    或可靠自动化接口时，执行构建、安装、运行和状态查询。

不能仅凭 IDE 进程存在，就判断项目已经成功运行。

### 7.3 缺少工具时的处理

选择：**提示用户缺少环境，并提供安装指引**。

第一阶段不要求 DevPilot
自动安装缺失软件。应说明缺少的工具、检测结果、建议版本和官方安装入口。

### 7.4 自定义外部工具

支持用户配置：

-   工具名称。
-   可执行文件路径。
-   启动参数。
-   工作目录。
-   关联项目。
-   可选的状态检测方式或自定义命令。

这样后续新增 IDE、模拟器或其他开发工具时，不必修改核心代码。

## 8. 第七轮：AI Agent 权限、安全与自主执行

**状态：已确认，7.1---7.4 全部完成**

### 8.1 AI 操作权限

选择：八类权限全部开放。

  权限           能力范围
-------------- -----------------------------------------------
  项目分析       读取项目目录、配置文件、依赖文件和运行日志
  执行命令       执行 npm、mvn、gradle、python 等命令
  修改启动脚本   创建、修改和修复 BAT、SH、PowerShell 等脚本
  修改项目配置   修改环境变量、端口、依赖配置等
  修改项目代码   分析错误并在授权范围内修改项目代码
  自动重试       启动失败后分析日志、修复并重新启动
  管理开发环境   检测、配置和管理 Java、Node.js、Python 等环境
  Git 操作       查看状态、切换分支、提交等操作

"权限全部开放"表示产品具备这些能力，不代表每个项目、每次任务都自动获得无限制权限。实际执行仍必须经过权限控制层。

### 8.2 执行授权机制

选择：**方案 C------授权范围内自主执行，超出权限才询问**。

要求：

-   AI 在当前授权范围内可以自主分析、规划和执行。
-   超出权限范围时必须暂停并请求用户授权。
-   支持全局权限、项目级权限和任务级临时授权。
-   用户可以随时调整或撤销权限。
-   权限变更应记录审计日志。

### 8.3 AI 自动修复机制

选择：**方案 D------普通模式与 AI 自动修复模式可切换**。

#### 普通模式

-   自动分析错误。
-   生成修复方案。
-   展示文件修改差异。
-   用户确认后修改。
-   修复后验证。

#### AI 自动修复模式

-   自动分析错误。
-   在授权范围内生成并执行修复。
-   修改前备份文件。
-   记录修改差异。
-   自动重新启动或测试。
-   失败后进入受限制的诊断和重试流程。

#### 两种模式共同要求

-   修改前备份。
-   保存修改记录。
-   支持 Diff 差异对比。
-   支持回滚。
-   修复后进行验证。
-   不得擅自删除用户原有项目文件。
-   高风险操作仍须遵守安全授权规则。

### 8.4 自动诊断、修复与重试边界

选择：**方案 A------限制重试次数、超时和操作范围，超限停止并报告**。

建议初始默认值（尚未逐项确认，后续可调整）：

  限制项                                   建议默认值
-------------------- ------------------------------
  最大自动修复次数                               3 次
  单条命令超时                                 120 秒
  单次修复任务总时间                          10 分钟
  自动修复范围           当前项目及明确授权的关联服务

超过次数、超时或操作范围时：

1.  停止当前自动修复任务。
2.  停止本次任务创建且仍在运行的相关子进程。
3.  保留原始项目文件。
4.  保存错误日志和修复记录。
5.  生成故障分析报告。
6.  展示已经尝试的修复方法。
7.  提供下一步人工处理建议。

### 8.5 安全架构原则

**AI 负责思考和制定计划，核心执行引擎负责权限校验并实际执行。**

建议安全控制层统一负责：

-   权限校验。
-   命令风险检查。
-   操作范围检查。
-   超时控制。
-   重试次数控制。
-   文件备份和回滚。
-   进程归属与终止控制。
-   操作审计。
-   暂停、终止和异常恢复。

AI 不应绕过执行引擎直接操作系统资源。

### 9.1 桌面端开发框架（8.1）

> **决策已回填（2026-11-11）**：已选定 **方案 A Electron** 并实际落地：桌面壳 `apps/desktop`（Electron + BackendManager 拉起 Nest 后端）+ 渲染层 `apps/renderer`（Vite + React）。以下候选表保留作历史记录。

目前已提出三个候选方案，但用户尚未确认最终选择。

---------------------------------------------------------------------------------------------------------------------------------
  方案                    技术                    主要特点
----------------------- ----------------------- ---------------------------------------------------------------------------------
  A                       Electron                HTML、CSS、TypeScript/JavaScript、Chromium、Node.js；生态成熟，适合复杂桌面应用

  B                       Tauri                   Web 前端 + Rust；资源占用较低，系统能力强，但 Rust 有一定学习成本

  C                       Python + PySide6        Python 桌面开发；自动化生态丰富，适合快速原型开发
  ---------------------------------------------------------------------------------------------------------------------------------

初步建议：Electron。

原因：DevPilot 需要复杂的项目管理 UI、日志面板、AI
对话窗口、插件扩展和大量本地系统操作。Electron 与 TypeScript/Node.js
生态结合紧密，适合快速构建 Windows 第一版并为后续跨平台适配做准备。

### 9.2 8.1 待确认内容

-   主要考虑因素：
    -   综合开发效率、生态成熟度和长期扩展性。
    -   性能、内存占用和安装包体积。
    -   开发简单、容易维护、方便 AI 辅助编程。
    -   第三方库和插件生态。

**【决策更新 2026-11-11】8.1 已按 Electron 落地实施（见 9.1 回填）。同时以下配套选型已随实现确定：**

-   本地数据库：better-sqlite3（单文件 devpilot.db，WAL）
-   进程管理：Node child_process + 会话 pid 表 + 停止时进程树清理
-   Agent 架构：自研 Supervisor 状态机（LangGraph.js 评估仍未做，见未完成工作清单）
-   密钥存储：暂为环境变量 + credentials.json(0600)（Windows 凭据管理器接入在 backlog）
